## Reusable architecture

- **Scene organization:** `rt64_scene.cpp` keeps a scene-level set of instances and views plus a separate light array. `rt64_instance.cpp` makes each instance refer to a reusable mesh and carries current and previous transforms, material, textures, shader, viewport, scissor, and flags. `rt64_mesh.cpp` owns packed vertex/index data and builds a bottom-level acceleration structure when ray tracing is enabled. This separation maps well to a CPU scene snapshot: immutable/cached mesh geometry, per-frame instances, frame camera, materials, textures, and lights. Keep SM64-specific collection in `gfx_pc.c`; don’t import RT64’s D3D device or resource wrappers.
- **Material semantics:** `RT64_MATERIAL` in `public/rt64.h` includes texture identities, N64 combiner inputs, vertex-derived specular, self-light, light-group masks, fog parameters, alpha/shadow controls, depth/ray bias, reflectance, and refraction. Its `enabledAttributes` mechanism supports partial per-instance overrides. For this port, use a compact stable material key derived from combiner ID, texture IDs, and raster state, then carry explicit optional ray material fields. Avoid using ephemeral GPU object pointers as material identity.
- **Lighting:** `Lights.hlsli` selects point lights by a bit mask and approximate intensity, uses radius-based falloff, and samples area-light positions with blue noise for soft shadows. The same file contains first-hit shadow traversal and diffuse/specular terms. The useful parts are the data model (position, diffuse/specular color, radius, point radius, attenuation, group bits) and staged quality controls. Port the math to Metal only after the raster result and scene-space units are verified.
- **Ray generation:** `PrimaryRayGen.hlsl` jitters camera rays, traverses transparent surfaces, and writes a set of G-buffer-like outputs: diffuse, world position/normal/specular, instance ID, depth, motion flow, reactive/lock masks, transparency, reflection, and refraction. Direct lighting traces shadow rays; indirect lighting samples a cosine hemisphere; reflection uses a reflected view ray and Fresnel weighting; refraction uses a refracted ray. These are separate techniques and passes, not a single monolithic shader.
- **Temporal stability:** direct and indirect passes reproject using motion flow, then attenuate history according to depth and normal agreement. They cap running history at 64 samples. `Random.hlsli` and `BlueNoise.hlsli` drive spatial/temporal samples. The principle to adopt is history rejection from geometry/camera motion; tune history length and sampling for mobile after profiling.
- **Composition:** `ComposePS.hlsl` combines diffuse with direct and indirect lighting, then adds reflections, refraction, and transparent contributions. The view schedules primary, direct, indirect, refraction, reflection, filtering, and composition as distinct steps in `rt64_view.cpp`. `GaussianFilterRGB3x3CS.hlsl` applies a small edge-aware-in-practice spatial smoothing approximation to direct/indirect buffers, but it is not a substitute for robust temporal denoising.

## Fit for the Metal/A16 design

Adopt the conceptual records and pass boundaries, not the Windows implementation. DXR `TraceRay`, HLSL ray-generation/hit groups, D3D12 descriptor heaps, resource barriers, shader binding tables, and the NVIDIA helper BLAS/TLAS generators are not portable. The current A16 path should use Metal compute kernels that traverse a software BVH. Build a BLAS per cached mesh and a top-level instance structure; refit animated geometry/transforms when topology is stable, rebuild only when buffers or topology change. Use explicit bounded traversal stacks and measure stack depth, divergence, memory traffic, and transparent multi-hit cost on A16 before adding more effects.

Our capture seam must preserve local-space triangle positions, optional normals/UV/color inputs, indices, stable mesh and instance identities, material identity, current and previous transforms, camera/view-projection history, and relevant lights. This supports instancing, motion vectors, material evaluation, and either software BVH traversal or newer-device Metal acceleration structures later. RT64’s instance vector indices are useful within its scene, but the SM64 capture layer should assign stable identities independently so history survives object-list churn.

Recommended order remains raster parity, capture tests, CPU BVH build/traversal tests, reduced-resolution compute shadows, then temporally accumulated direct lighting. Reflections, indirect bounces, and denoising should wait for measured A16 cost and validated motion rejection. No RT64 ray-tracing behavior is claimed as implemented here.
