# SHADER64 Mission 81: architecture and API 2

## Current renderer map

```text
Fast3D / WSC command stream
  -> native CC combiner feature generation
  -> per-batch Metal vertex layout and native MTLRenderPipelineState
  -> offscreen RGBA16Float scene target (when effects or SHADER64 need it)
  -> built-in AO / bloom / god-rays / shadows / final composite, or SHADER64
  -> drawable
  -> native HUD and developer UI
```

`gfx_metal.c` is not a generic scene graph renderer: `gfx_metal_vertex_layout.h` describes the existing per-batch vertex data. The leading attribute is clip-space `float4`; optional fields include UV0/UV1, fog, and up to four combiner inputs. Normals, object identifiers, and a general world transform are not part of that draw interface. `gfx_scene_capture` separately records bounded world-space triangles with normals, UVs, colors, material/texture identifiers, camera matrices, and object transforms when it can split the model-view matrix. That capture currently feeds specific AO/shadow work; it is not yet a general programmable geometry submission path.

WSC materials are translated through the existing scene-material and Fast3D/combiner interface in `gfx_pc.c`; WSC geometry is not a separate renderer. WSC4/WSC5 content keeps that native batch path, and the post-combiner material hook can vary its output by world/object/character class. Pack textures, view-space positions, optional lit-vertex normals, and the graph's depth-derived scene resources add opt-in customization without changing WSC file requirements. This does not expose arbitrary WSC material metadata or replace native material decoding.

| Information | Existing engine path | API 1 / API 2 status |
|---|---|---|
| Final scene color | Resolved/offscreen Metal color texture | Exposed to both postprocess APIs |
| Depth and inverse projection | Native sampleable single-sample depth plus frame matrices | Optional graph inputs; depth is nonlinear Metal depth and must be reconstructed |
| AO and built-in shadow output | Native AO/shadow and final-composite passes | AO is not separately exposed; one native shadow map and its world-to-shadow basis are available to opted-in API 2 passes |
| World/view positions and transforms | Bounded scene capture and opt-in Fast3D view positions | Material hooks can receive view-space positions; graph passes can reconstruct world positions from depth/inverse-view. Per-object world transforms are not a general shader input. |
| Normals | Fast3D-lit vertex payloads when present, plus depth-derived view normals | Lit source normals are opt-in to material hooks; reconstructed scene normals are optional graph inputs. Neither is guaranteed for all geometry. |
| Fast3D UV/color/combiner inputs | Per-batch vertex layout and generated shader | UV and post-combiner base color are exposed to material hooks; arbitrary attributes and pre-combiner stages are not. |
| WSC material category and textures | Existing scene-material flags and texture IDs | World/object/character class is exposed; manifest PNGs can bind to opted-in material/graph shaders. Native WSC metadata is not a general shader binding contract. |
| Motion vectors/history | No stable per-vertex motion stream | Unsupported |
| HUD | Separate native overlay after scene composite | Remains outside custom graph |

## API 2 vertical slice

API 2 (`formatVersion: 2`, `shaderApiVersion: 2`) is a Metal-native fullscreen raster DAG. It is intentionally a small first slice, not a claim of Iris/OptiFine compatibility. Each pass compiles its own Metal source with the common `shader64_pass` entry. The engine supplies a fullscreen triangle, one sampled input image, one clamp/linear sampler, and four pack parameters. Passes write either a named RGBA16Float sampled target or the drawable resource `present`.

The Fast3D/GeoLayout integration tags iOS Metal display-list items as static world, dynamic object, or Mario. An optional API 2 `materialShader` hook now runs after the existing N64 combiner and fog calculation, so packs can change the resulting color by material class while the Fast3D material remains the input and authority. Its baseline entry point is `float4 shader64_material(float4 baseColor, float2 uv, float4 screenPosition, uint materialClass, constant float4 &params)`. Class IDs are 0 unclassified, 1 world, 2 object, and 3 character. UV is zero when the Fast3D draw has no texture coordinates; `screenPosition` is the Fast3D raster position, not a world-space position; `params` is the API 2 four-float parameter vector. Each draw receives the class through the fragment constant block. A selectable Material Class diagnostic visualizes the same classification.

A material may opt in to source vertex normals with `"vertexNormals": true` in its `materialShader` manifest object. The signature becomes `shader64_material(baseColor, uv, screenPosition, materialClass, viewNormal, normalValid, params)`, where `viewNormal` is a normalized view-space normal produced from the signed SM64 vertex-normal payload using the modelview inverse transpose. `normalValid` is false when the display list did not provide lighting normals or the transform is singular; shaders should preserve `baseColor` in that case. This adds one float4 vertex attribute only for the active opt-in pack. It uses normals available in Fast3D-lit vertices; it does not synthesize normals for unlit geometry. WSC geometry can provide them only when its source/display-list path carries valid lighting-normal data. `VertexNormal64` is a diagnostic example, not proof of rendered pixels. Packs that do not opt in keep the existing material layout and combiner path.

With `"directionalLight": true`, the signature adds `float3 sunDirectionView, float sunIntensity` before the pack parameters. It requires either `vertexNormals:true` or `vertexPositions:true`, so the shader has actual geometry data from which to use or derive a normal. The direction is the renderer's selected sun direction rotated from world space into the captured camera's view space and normalized. Intensity follows the existing renderer's sun setting and is zero if effects are disabled or camera data is unavailable. Only camera matrices are retained for this material-only input; per-triangle capture remains reserved for features such as shadow maps that consume geometry. `SunlitMaterial64` demonstrates diffuse shading from source normals; `GeometryNormal64` derives flat normals with fragment derivatives before applying the configured sun. Neither example has been visually verified on an iPhone.

An independent `"vertexPositions": true` option adds `float3 viewPosition, bool positionValid` before the pack parameters. Position is transformed from Fast3D object-space vertex coordinates by the row-vector modelview matrix, then homogenized; a non-finite or singular result is marked invalid. This is actual view-space geometry data, not a reconstruction from raster coordinates. `SurfacePosition64` demonstrates geometry-dependent material color. Positions and normals are separately opt-in; when both are requested, the generated attribute order and packed VBO layout match. API 1 and packs without these options retain the original vertex layout.

Material fragments may also use Metal's fragment derivatives on `viewPosition`. `GeometryNormal64` derives a flat face normal with `cross(dfdx(viewPosition), dfdy(viewPosition))`, flips it toward the view-space camera, and applies one-sided diffuse lighting. The camera-facing correction makes reversed winding produce the same oriented normal for visible faces; invalid/degenerate inputs fall back to the base color. This is intentionally a flat per-triangle/screen-derivative result and can be discontinuous; it does not synthesize a smooth vertex normal or alter the engine's source normals. Host math covers representative floor, wall, and slope fixtures, but actual MSL fragment derivatives and image quality still need device validation.

The material hook does **not** provide direct world-space positions, per-object transforms, arbitrary native material metadata, or pre-combiner control. It is a post-combiner fragment customization point, not a programmable geometry/deferred renderer. It can opt into Fast3D UVs, pack-owned textures, valid view-space positions, lit-source view normals, and the configured sun. Graph passes separately may request depth, depth-derived view normals, lighting/camera matrices, native shadow resources, and pack textures within documented binding combinations. Failed shader generation/compilation is logged and falls back to the original Fast3D combiner for that program, preserving gameplay/render recovery rather than presenting an unsupported shader as active success.

An API 2 pass may opt into the auxiliary `sceneDepth` resource with `"sceneDepth": true`. It then implements `shader64_pass_depth(color, uv, image, imageSampler, sceneDepth, depthSampler, inverseProjection, params)`. `sceneDepth` is the native Depth32Float hardware depth sampled over the scene viewport; its values are nonlinear Metal depth in [0,1], and 1 represents clear/background. `inverseProjection` is the current engine inverse projection matrix; screen UV maps x to [-1,1] and flips y to Metal clip coordinates, while depth is mapped from [0,1] to [-1,1] before unprojection. Scene depth is read-only and bound only for opted-in passes. Camera capture is enabled only while a graph requests it. If a valid single-sample depth texture or projection is unavailable, the renderer logs and uses its built-in final composite for that frame. Custom passes that need linear/view-space values must reconstruct them from this documented pair; no normals or world positions are implied.

An API 2 fullscreen pass may instead request `"sceneNormals": true` and implement `shader64_pass_normals(color, uv, image, imageSampler, sceneNormals, normalSampler, params)`. The engine derives normals from neighboring samples of scene depth and inverse projection in a compute pass, then binds a half-resolution private RGBA16Float texture. RGB stores a view-space normal encoded from [-1,1] to [0,1]; alpha 1 marks a valid reconstruction and alpha 0 marks sky or a depth discontinuity. This is a screen-space estimate, not native vertex normals or a world-space G-buffer. It requires single-sample scene depth. Fullscreen resource combinations remain restricted by their existing binding layout. It can be combined with `packTextures`: the extended entry point is `shader64_pass_normals_textured` and keeps normal at texture 1 and pack images at slots 4–7. `NormalDebug64` and `NormalTexture64` demonstrate the fullscreen contracts. Xcode 27 MSL compilation has passed; orientation/edge appearance and actual GPU output still need device validation.

Reference diagnostic packs now use only these public resources: `DepthDebug64` shades raw nonlinear depth, `NormalDebug64` displays the engine's reusable depth-derived view-space normal resource, and `MaterialDebug64` colors the existing world/object/character class signal through the external material hook. The normal display is not a native per-vertex normal attachment and is expected to have discontinuity artifacts at silhouettes.

Passes may also request `"sceneLighting": true`. This implies scene depth and supplies the current inverse projection, inverse view, and `sunDirectionAndIntensity` (world-space direction in xyz, configured engine intensity in w). The pass must implement `shader64_pass_lit`; `Lumen64Graph` demonstrates per-pixel directional diffuse shading from a view normal reconstructed from depth. Its ambient floor is a pack parameter. This is a depth-derived screen-space lighting technique: it has silhouette/edge artifacts, no material-specific roughness or world position, and no custom shadow-map input. It is separate from the built-in engine shadow-map receiver and does not claim global illumination.

Passes may request `"sceneShadows": true` to consume the native directional shadow map. This implies scene depth and lighting and uses the `shader64_pass_shadowed` contract, with scene depth at texture 1, shadow depth at texture 2, inverse projection/view and sun inputs at buffers 1–3, and the fitted world-to-shadow basis/ranges at buffers 4–7. `Lumen64ShadowGraph` reconstructs position and normal from real scene depth and performs a 3×3 PCF comparison against the renderer's shadow map. That map uses the existing bounded scene-capture geometry path (up to 8192 source triangles). When the map, world-space caster set, or valid camera matrices are unavailable, that graph falls back to the built-in final composite for the frame. This is one existing native shadow map, not a general user-defined shadow-camera/pass system; coverage, filtering quality, and appearance still require physical-device validation.

Passes may request `"packTextures": true` and use `shader64_pass_textured`. The pack manifest declares an ordered `textures` array of at most four `{id, source}` objects; source paths must be direct `textures/*.png` paths. Bindings are `packTexture0..3` and their samplers at slots 4–7, `packTextureCount` at buffer 1, and normal API 2 params at buffer 0. Slots beyond count alias slot zero; count lets a shader avoid depending on aliases. This initial contract cannot be combined on one pass with scene depth, scene lighting, or scene shadows. The installer bounds each PNG to 4 MiB and the complete ZIP to 8 MiB; iOS decoding limits each dimension to 2048 and the pack to 4 megapixels before allocating its RGBA buffer. Images upload as premultiplied RGBA8, and active graph ownership keeps them alive through in-flight command buffers. Missing or invalid textures reject candidate activation and leave the prior graph active. `TextureDemo64` is a generated checker-pattern reference pack.

```json
{
  "formatVersion": 2,
  "id": "ExampleGraph",
  "name": "Example graph",
  "author": "Author",
  "version": "1.0",
  "shaderApiVersion": 2,
  "stage": "render_graph",
  "materialShader": {"source":"shaders/material.metal"},
  "parameters": [
    {"name":"characterTint", "label":"Character tint", "type":"float", "default":0.65, "min":0, "max":1}
  ],
  "passes": [
    {"id":"first", "type":"fullscreen", "input":"sceneColor", "output":"filtered",
     "source":"shaders/first.metal", "scale":0.5},
    {"id":"final", "type":"fullscreen", "input":"filtered", "output":"present",
     "source":"shaders/final.metal", "scale":1.0}
  ]
}
```

`materialShader` is optional. Its source file implements the hook above and is capped at the same 256 KiB source limit as graph passes. The material hook shares the graph pack's four parameters. GraphDemo uses its fourth parameter to tint only material class 3, leaving static world geometry on the original combiner output. A material may declare `"packTextures": true`; this enables the same manifest-ordered `textures` array for actual Fast3D material shading. The texture-aware contract passes `materialTexture0..3`, samplers, and `materialTextureCount` to `shader64_material`; absent slots alias slot zero, and count is authoritative. Texture resources share the existing four-image / four-megapixel bounds and graph-owned lifetime. `"vertexNormals": true` opts into source normals, `"directionalLight": true` additionally opts into the camera-space sun input and requires normals, and `"vertexPositions": true` opts into true view-space vertex coordinates. The runtime validates optional signatures independently, including when combined. Paper64MaterialGraph exercises paper-grain modulation, VertexNormal64 visualizes available source normals, SunlitMaterial64 demonstrates directional diffuse shading, and SurfacePosition64 uses per-vertex geometry position. Host import and code-generation tests cover these interfaces; Apple MSL and physical-device verification are tracked separately.

Each source declares `float4 shader64_pass(float4 color, float2 uv, texture2d<float> image, sampler imageSampler, constant float4 &params)`. The generic `color` argument is the current input sample. Passes can read nearby texels from `image`; they cannot access depth or other pass outputs except through the declared input edge.

Initial limits: four passes, three named intermediate targets, direct `shaders/*.metal` files, 256 KiB source per pass, full-resolution `present`, 0.25–1.0 scale for intermediate targets, and a 32 MiB RGBA16Float intermediate-target budget. The graph rejects duplicate IDs/resources, undeclared reads, feedback, cycles, unconsumed targets, unsupported node types, and invalid scales. The iOS runtime rechecks actual drawable dimensions against the byte budget. Candidate sources and pipelines compile before activation; failure preserves the currently active API 1/API 2 renderer. GPU programs remain untrusted and cannot be safely preempted by source validation.

API 2 also accepts bounded `"type":"compute"` intermediate nodes. The fixed Metal kernel contract is `shader64_compute(image [[texture(0)]], output [[texture(1)]], params [[buffer(0)]], frameInfo [[buffer(2)]], tid [[thread_position_in_grid]])`; input and output are read/write `texture2d<float>` resources, and compute output cannot target `present`. `frameInfo` is a float4 of elapsed seconds, clamped frame delta seconds, frame index, and output aspect ratio. A pass may opt into its manifest's bounded PNG list with `"packTextures": true`; those read-only textures occupy slots 2–5 and `packTextureCount` is buffer 1. It may request `"sceneDepth": true`; the engine binds native single-sample nonlinear depth at texture/sampler 6 and inverse projection at buffer 3. It may also request `"sceneNormals": true`; the engine binds its half-resolution, depth-derived view-space normal texture at texture/sampler 7. A pass may request `"sceneLighting": true` to receive inverse-view transform at buffer 4 and configured world-space sun direction/intensity at buffer 5; this requires both `sceneDepth` and `sceneNormals`. It may request `"sceneShadows": true` to receive the native shadow depth texture at texture/sampler 8 and the fitted world-to-shadow basis at buffers 6–9; compute shadows require depth, normals, and directional lighting. Pack textures, depth, normals, lighting, and the native shadow map use disjoint bindings and can be combined in one compute node. The shadow map is the existing bounded native map, not a user-defined shadow pass, and availability still depends on the map/caster path succeeding for that frame. Compute nodes cannot add undeclared texture/buffer bindings. They use the same four-pass, three-target, per-target 32 MiB graph budget and 0.25–1.0 resolution bounds as raster nodes. `ComputeBlur64`, `ComputeTexture64`, `DepthCompute64`, `DepthNormalsCompute64`, and `SceneDataCompute64` demonstrate filtering, user textures, depth fog, depth/normal shading, and a node combining imported texture, scene resources, configured sunlight, and shadow visibility respectively; each routes output to a generic fullscreen presentation pass. Before activation, source validation checks the fixed binding contract and Metal pipeline reflection checks active resource slots and access modes. This is not a GPU execution sandbox: shader authors can still write costly or nonterminating GPU work, and only runtime/device testing can establish its behavior.

Fullscreen raster passes may separately request `"frameInfo": true` and implement `shader64_pass_frame(color, uv, image, imageSampler, params, frameInfo)`. The engine binds the same float4 at fragment buffer 8; this initial variant is limited to otherwise generic fullscreen passes to keep resource interfaces unambiguous. `AnimatedGraph64` demonstrates a time-varying color pulse. Ordinary API 2 fullscreen contracts remain unchanged.

Metal encoder ordering provides the pass sequence on one command buffer; render attachments use explicit render-target and shader-read usage. Textures are retained with the active graph until command-buffer completion. Metal's documented resource-ordering guarantees and completion handlers are used; no manual memory barrier is added for this serial render-encoder chain. Intermediate textures are not memoryless because later passes sample them. Apple documents render pass attachment/load/store behavior, resource synchronization, and runtime source compilation here: [render pass descriptor](https://developer.apple.com/documentation/metal/mtlrenderpassdescriptor), [resource synchronization](https://developer.apple.com/documentation/metal/resource-synchronization), and [runtime Metal source compilation](https://developer.apple.com/documentation/metal/mtldevice/makelibrary%28source%3Aoptions%3Aerror%3A).

## Showcase64 full-resolution composition input

The API 2 optional pass property `"sceneColorSource":true` gives a fullscreen pass the original full-resolution scene texture as an additional read-only input at texture/sampler 9. It is restricted to a full-resolution pass writing `present` and cannot be combined with the other optional pass resources. The helper signature is `shader64_pass_scene_color(color, uv, image, imageSampler, sceneColor, sceneColorSampler, params)`. This supports effects computed at a lower resolution and composited over the unscaled original frame. Existing packs need not request it.

`Showcase64` uses this resource to compute bounded half-resolution screen-space atmospheric scattering from scene depth and the existing directional shadow map, then composites the radiance/transmittance over full-resolution scene color. It also opts into a directional Fast3D material hook using view-space positions. See [`SHADER64_SHOWCASE64.md`](SHADER64_SHOWCASE64.md) for device instructions and the limitations: this is not path tracing, has no temporal history or material roughness/water classification, and bypasses the built-in final composite while active. Host tests do not establish Metal GPU output; physical iPhone appearance and frame time remain pending.

Bliss uses GLSL features and Iris/OptiFine naming conventions; there is no direct source execution path through Metal. A reusable translator can be evaluated later as a front end for a restricted GLSL subset (preprocessor, type/system-function compatibility, sampler and stage lowering), but it cannot replace semantic adapters for Minecraft uniforms, geometry stages, shadow maps, compute, or G-buffers. API 2 remains authored in Metal; no GLSL translator is implemented in this increment.

The inspected Bliss license permits sharing modified shader versions only with its attribution, title, non-monetization, and redistribution conditions. The sample pack is a small independently expressed adaptation of the optional `CAMERA_GRIDLINES` behavior in Bliss's `dimensions/final.fsh`, titled `-Bliss Camera Gridlines Adaptation- (Chocapic13' Shaders edit)`, and includes the archive's license text and attribution. The archive itself and its other shader sources/assets are not copied into the repository. This pack is an effect-level compatibility proof, not a conversion of Bliss as a whole.

## Explicitly unsupported in this milestone

API 2 supports bounded fullscreen raster nodes, fixed-contract image compute nodes, and a post-combiner material hook. The engine directional shadow map is an optional sampled input, but user-defined shadow cameras/pass nodes are not supported. Pack PNGs are available to opted-in fullscreen, compute, and material passes. Compute nodes can combine pack textures, scene depth, and depth-derived scene normals in fixed, non-overlapping bindings; fullscreen resource combinations retain their documented binding restrictions. Geometry-stage overrides, deferred lighting, native per-pixel normal/albedo/material G-buffer attachments, history/ping-pong, pass dependencies beyond one sampled input, configurable load/store/stencil, resource aliasing/heaps, device-feature declarations/fallbacks, include files, and GLSL translation are unsupported and not advertised. API 1 source and `.metallib` loading remain available. API 2 graph nodes accept Metal source only; external `.metallib` graph nodes are not supported yet.
